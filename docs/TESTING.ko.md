# GhostFlow 적합성 및 신뢰성 테스트

상태: 규범적 테스트 정책.

현재 테스트 모음이 통과했다는 사실은 그 실행이 명시한 요구 사항과 구성에 대한
증거일 뿐입니다. 언어 전체나 물리 Farm Device가 검증되었다고 주장하는 것은
**아닙니다**.

## SQLite에서 영감을 받은 원칙

GhostFlow는 SQLite의 테스트 규율 중 작고 이식 가능한 제어 언어에 맞는 부분을
채택합니다.

1. **테스트 가능한 모든 규범 문장은 요구 사항입니다.** 각 요구 사항에는 내용에서
   파생된 안정적인 ID와 정확한 소스 위치가 있습니다. 또한 실행 가능한 테스트나
   명시적인 보류 사유 중 하나를 가집니다.
2. **공개 인터페이스와 배포되는 바이트를 테스트하십시오.** 파서 전용 테스트나 소스
   수준 테스트로는 GFB, native 런타임, WASM 동작을 입증할 수 없습니다.
3. **독립적인 하네스를 유지하십시오.** 컴파일러 테스트, GFB 로더/검증기 테스트,
   native 실행, WASM 실행, 호스트 수명주기 테스트는 서로 다른 결론을 낼 수 있어야
   합니다.
4. **모든 경계의 양쪽과 모든 불리언 판단을 시험하십시오.** 선언된 한도에는 최소,
   최대, 바로 안쪽, 바로 바깥쪽 사례가 필요합니다.
5. **각 원자적 경계에서 실패를 주입하십시오.** 실패할 때마다 불변 조건을
   확인하십시오. 거부된 컴파일, 로드, tick, 리셋, 핫스왑, 영속화 작업은 부분 상태나
   부분 출력 집합을 조용히 확정해서는 안 됩니다.
6. **잘못된 형식의 artifact와 변조된 artifact를 일반적인 적대적 입력으로
   다루십시오.** 로더는 패닉 없이 이를 거부하거나, 별도로 유효한 모듈로 받아들여야
   합니다. 변조본이 원본과 동등하다고 절대 가정하지 마십시오.
7. **같은 artifact와 같은 입력 trace로 독립적인 구현이나 대상을 비교하십시오.**
   native와 WASM은 일치해야 합니다. 두 대상은 같은 코어의 의미를 공유하므로, 그
   공유 의미에 대해서는 여전히 별도의 오라클이 필요합니다.
8. **테스트 자체를 측정하십시오.** 분기/조건 커버리지와 변이 테스트는 재현 가능한
   명령과 정당화된 제외 항목이 체크인되면 릴리스 게이트가 됩니다. 테스트 개수로
   커버리지 백분율을 절대 추정하지 마십시오.
9. **수정한 모든 결함에는 회귀 테스트가 붙습니다.** 수정이 수용되기 전에 최소한의
   영구 회귀 사례가 있어야 합니다.
10. **릴리스 빌드에서 릴리스 테스트 모음을 실행하십시오.** 릴리스 모드 artifact와,
    소비자가 배포하는 것과 같은 기능 구성을 사용하십시오.

이 정책은 SQLite가 공개적으로 설명하는 요구 사항 카탈로그, TH3 배포 상태 그대로의
테스트, 경계 및 결함 주입 루프, 독립적인 SQL Logic Test 비교, 분기/MC/DC 커버리지,
변이 테스트에서 영감을 받았습니다. GhostFlow가 SQLite 수준의 커버리지나 보증
수준에 도달했다고 주장하지는 않습니다.

## 요구 사항 기록

`contracts/requirements/` 아래의 기계 검사 카탈로그는 각 요구 사항에 대해 다음을
기록합니다.

- 정규화된 규범 텍스트에서 파생된 안정적인 ID
- 정확한 규범 텍스트와 그 문서 위치 지정자
- 담당 계층과 지원 대상
- 해당 문장을 실행하는 테스트의 ID, 또는 비어 있지 않은 보류 사유
- 검증됨, 부분 검증됨, 보류된 작업을 구분하는 상태

규범 텍스트를 변경하면 새 ID가 생성됩니다. 이전 기록은 대체된(superseded) 이력으로
계속 남습니다. 이렇게 하면 오래된 테스트가 입증한 내용이 조용히 바뀌는 일이 절대
없습니다.

## 검증 계층

각 계층에는 고유한 증거가 필요합니다. 표는 계층별 최소 요건을 보여 줍니다.

| 계층 | 최소 증거 |
| --- | --- |
| 문법 | 정확한 진단을 포함하는, 수락 및 거부되는 token/AST 사례 |
| 타입과 하향 변환 | 타입이 지정된 소스에서 검사된 GFB 구조와 manifest까지 |
| GFB 검증기 | 유효한, 잘린, 한도를 넘는, 변조된 바이트 시퀀스 |
| native VM | 정확한 상태, 요청 의도, 안전 의도, fault, 원자성 trace |
| WASM VM | native와 같은 artifact/trace와 오류 분류 |
| 호스트 수명주기 | 설치, 활성화, 첫 스캔, 실패한 스캔, 리셋, 핫스왑, replay |
| 제품 어댑터 | 식별된 언어 artifact만 사용, 중복 평가기 없음 |
| Device | 별도의 빌드, board/profile, 드라이버, 물리 관측 게이트 |

## 출력 안전 규칙

**`output` 선언이란.** `output` 선언은 논리적 의도 포트에 이름과 타입을 부여합니다.
상태를 유지하지 않습니다. 물리 릴레이의 시작 레벨이나 페일세이프 레벨을 구성하지도
않습니다. 선언된 모든 출력에는 스캔마다 평가되는 연결식이 정확히 하나 있습니다.
상수 의도를 출력하려면 상수 연결식을 작성하십시오.

**첫 번째 성공 스캔 전.** 아직 VM 출력 의도가 없습니다. 호스트/렌더러는 구성된
안전 상태를 유지해야 하며, 기본 Farm Device 정책은 OFF입니다. 컴파일, 로드, 활성화,
tick 실패가 소스 구문에서 의도를 만들어 낼 수는 없습니다.

**물리적 안전의 담당.** 물리적 시작, 워치독, 페일세이프 정책은 식별된 호스트
바인딩에 속합니다. 이들은 이식 가능한 VM 프로그램과 분리된 상태로 유지됩니다.
