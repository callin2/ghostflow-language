# GhostFlow 一致性与可靠性测试

状态：规范性测试策略。

当前测试套件的一次通过运行，仅能作为该运行所列出的需求和配置的证据。它**不**声称整个语言或某台实体 Farm Device 已经过验证。

## 借鉴 SQLite 的原则

GhostFlow 采纳了 SQLite 测试纪律中适合小型、可移植控制语言的部分：

1. **每一条可测试的规范性陈述都是一项需求。** 每项需求都有一个稳定的、由内容派生的 ID 和精确的源位置。它要么有可执行测试，要么有明确的待定理由。
2. **测试公开接口和部署的字节。** 仅针对解析器或源码层面的测试无法确立 GFB、原生运行时或 WASM 的行为。
3. **保持相互独立的测试框架。** 编译器测试、GFB 加载器/校验器测试、原生执行、WASM 执行以及宿主生命周期测试必须能够彼此得出不同结论。
4. **覆盖每个边界的两侧和每个布尔判定。** 已声明的限值需要最小值、最大值、刚好在内和刚好在外的用例。
5. **在每个原子边界注入故障。** 每次故障后都要检查不变量。被拒绝的编译、加载、tick、重置、热替换或持久化操作，不得悄悄提交部分状态或部分输出集。
6. **把格式错误和被篡改的构件视为普通的恶意输入。** 加载器必须要么在不 panic 的情况下拒绝它们，要么把它们作为另一个独立有效的模块接受。绝不假定被篡改的构件与其源等价。
7. **使用相同构件和相同输入追踪，比较相互独立的实现或目标。** 原生与 WASM 必须一致。由于两个目标共享来自同一 core 的语义，对于这些共享语义仍需要一个独立的判定基准（oracle）。
8. **度量测试本身。** 一旦可复现的命令和有正当理由的排除项被签入，分支/条件覆盖率和变异测试就成为发布关卡。绝不从测试数量推断覆盖率百分比。
9. **每个已修复的缺陷都要有回归测试。** 在修复被接受之前，必须提供一个最小的、永久的回归用例。
10. **在发布构建上运行发布测试套件。** 使用发布模式的构件以及使用方部署时相同的功能配置。

本策略借鉴了 SQLite 公开描述的需求目录、TH3 按部署形态测试、边界和故障注入循环、独立的 SQL Logic Test 比较、分支/MC/DC 覆盖率以及变异测试。它并不声称 GhostFlow 已达到 SQLite 的覆盖率或保证水平。

参考资料：

- <https://www.sqlite.org/requirements.html>
- <https://www.sqlite.org/testing.html>
- <https://www.sqlite.org/th3.html>

## 需求记录

`contracts/requirements/` 下由机器检查的目录为每项需求记录：

- 由规范化后的规范性文本派生的稳定 ID；
- 精确的规范性文本及其文档定位符；
- 所属层级和支持的目标；
- 覆盖该陈述的测试 ID，或一个非空的待定理由；
- 区分已验证、部分验证和待定工作的状态。

修改规范性文本会产生新的 ID。先前的记录作为已被取代的历史继续保留。这样，旧测试所证明的内容永远不会被悄悄改变。

## 验证层级

每个层级都需要各自的证据。下表列出了每层的最低要求。

| 层级 | 最低证据 |
| --- | --- |
| 语法 | 被接受和被拒绝的 token/AST 用例，带有精确的诊断 |
| 类型与降级（lowering） | 从带类型的源码到经过检查的 GFB 结构和清单 |
| GFB 校验器 | 有效、截断、超限和被篡改的字节序列 |
| 原生 VM | 精确的状态、请求意图、安全意图、故障和原子性追踪 |
| WASM VM | 与原生相同的构件/追踪和错误类别 |
| 宿主生命周期 | 安装、激活、首次扫描、失败的扫描、重置、热替换和重放 |
| 产品适配器 | 仅限已标识的语言构件；不得有重复的求值器 |
| 设备 | 独立的构建、板卡/profile、驱动程序和物理观测关卡 |

## 输出安全规则

**输出声明是什么。** 输出声明为一个逻辑意图端口命名并赋予类型。它不保存状态，也不配置物理继电器的启动电平或故障安全电平。每个已声明的输出恰好有一个逐扫描的连接表达式。要输出常量意图，请编写一个常量连接表达式。

**在第一次成功扫描之前。** 此时还没有 VM 输出意图。宿主/渲染器必须保持其配置的安全状态；Farm Device 的默认策略是 OFF。编译、加载、激活或 tick 失败不能根据源码语法凭空产生意图。

**谁负责物理安全。** 物理启动、看门狗和故障安全策略属于已标识的宿主绑定，它们与可移植的 VM 程序保持分离。
