# 永続的なローリング予算の説明

**ローリング予算**は、スライドする時間ウィンドウ内でリソースが ON でいられる時間を制限します（たとえば「任意の 60s のうち ON 時間は最大 30s」）。その予算によって起動が拒否されたとき、オペレーターやツールは、*なぜ*拒否されたのか、*いつ*許可されうるのかを知る必要があります。`explainRolling` は、何も変更せずにその両方に答えます。

**呼び出し。** `AccountingRuntime.explainRolling({ nowMs, windowMs, limitMs, reserveMs })` は、検査済みソースに結び付けられた永続的な `on_time` アカウントを読み取ります。

- 検査済みの正本ソースが、唯一のローリングウィンドウ、上限、提案される予約を選びます。引数がソースと一致しない場合、呼び出しは拒否されます。
- コピーされた不変のバインディングは、呼び出し側が公開メタデータを編集しようとしても、そのポリシーを保持します。

**結果**には次のものが含まれます。

- 正本ソースの SHA とアーティファクトの SHA
- アカウント/対象と、明示的なホストリソース ID
- クエリ時刻
- 使用済み継続時間（適用区間の和集合）と、未決済の予約継続時間
- 上限と提案される予約量
- `blocked`、およびリクエストが拒否された場合の `blockReason: 'rolling-budget'`
- `nextReleaseMs` と `ledgerRevision`

**受け入れ（アドミッション）と同じ計算。** Rust の台帳（レジャー）は、実際の `reserveRolling` の受け入れが使うのと同じ適用区間の和集合と未決済の課金を計算します。そのため、説明の予算部分はその受け入れ判断と一致します。

**計算例。** 適用区間 [0,20s] と [10s,30s]、60s のウィンドウ、30s の上限、5s の提案を考えます。

- 40s の時点では、ウィンドウは [-20s, 40s] です。区間の和集合は 30s なので、30s が使用済みです。30s + 5s は上限の 30s を超えるため、リクエストはブロックされます。
- 最も早く受け入れ可能になる時刻は 65s です。このときウィンドウは [5s, 65s] で、使用済みは 25s、25s + 5s は上限に収まります。
- 64.999s ではリクエストはまだ拒否され、65s で予約できます。

![適用区間 [0,20s] と [10s,30s]、および 40s（ブロック）と 65s（受け入れ可能）で照会した 60s ウィンドウ](diagrams/rolling-budget-explanation/release-example.ja.svg)

このクエリは台帳を変更せず、起動を許可することもありません。容量不足や同一性の重複といった他の受け入れ失敗は、この予算の説明とは別に扱われます。

**`nextReleaseMs` が約束すること。** `nextReleaseMs` は、新しい証拠が到着しないことを前提とします。その他の規則は次のとおりです。

- 未決済の予約は、同一性によって明示的に決済またはキャンセルされるまで課金されたままです。時間の経過や OFF のアニメーションでは解放されません。
- それらの課金と提案の合計がすでに上限を超えている場合、時間の経過による解放は約束されません。
- 予算がすでに受け入れ可能な場合も、`nextReleaseMs` は null です。
- 有界の探索は、和集合のクエリを最大 64 回まで実行します。
- タイムスタンプは u64 の最大値で飽和し、決してラップアラウンドしません。
- 保存されたいずれかの区間の終端より前の時刻でクエリすると Unknown が返ります。未来の日付を持つ証拠からは、減少していく予測を確立できないためです。

**Unknown。** Unknown の場合は null が返ります。これには、未初期化または破損した状態と、未確認の変更（永続化がまだ確認されていない変更）が含まれます。

- 説明の証拠を生むのは、正確に永続化されたリビジョンだけです。
- リビジョン番号は、稼働中の所有者ごとにローカルです。復元後は、リビジョン 0 から再び始まります。
- 復旧では、永続スナップショットと正本ソースをリプレイします。再起動をまたいで残るリビジョンカウンタには依存しません。

**ホストの責任。** ホストは、検証済みの適用証拠、安定したリソースバインディング、比較可能で信頼できる単調なタイムラインを提供します。この API はクロックやバインディングのリビジョンを捏造せず、物理的な受領を認証することもありません。

**適合性（REF-04-066）。** REF-04-066 は、実際の WASM 台帳による拒否、正確な解放境界、永続化が保留中の間の Unknown、スナップショットの復元、制御の有効化を検証します。同じスナップショットから復元した別のコンテキスト台帳は、実際に完了した OFF の出力観測を生成します。その観測はローリングの拒否を引き起こさず、その台帳をリセットすることもありません。アニメーションはアカウンティング API への入力ではありません。

**範囲。** これはリファレンスとしての使用量計上（アカウンティング）の投影です。次のものでは**ありません**。

- フロントエンドの cabinet-view の検証
- コンパイル済みの `on_time` 起動/遮断との自動統合
- API のデプロイ
- 記憶媒体の認証
- Device の検証

追加された WASM エクスポートを使うには、WASM モジュールの再ビルドが必要です。GFB と台帳スナップショットの形式は変わりません。
