# GhostFlowの適合性と信頼性のテスト

ステータス：規範的なテスト方針。

現在のテストスイートが成功しても、それはその実行が名指ししている要件と構成についての証拠にすぎません。言語全体や物理的なFarm Deviceが検証済みであると主張するものでは**ありません**。

## SQLiteに着想を得た原則

GhostFlowは、SQLiteのテスト規律のうち、小さくポータブルな制御言語に適した部分を採用しています。

1. **テスト可能な規範的記述はすべて要件です。** 各要件は、内容から導出された安定したIDと、正確なソース位置を持ちます。そして、実行可能なテストか、明示的な保留理由のどちらかを持ちます。
2. **公開インターフェイスと配備されるバイト列をテストします。** パーサだけのテストやソースレベルのテストでは、GFB、ネイティブランタイム、WASMの振る舞いを立証できません。
3. **独立したハーネスを維持します。** コンパイラのテスト、GFBローダー／検証器のテスト、ネイティブ実行、WASM実行、ホストのライフサイクルのテストは、互いに食い違う結果を出せるものでなければなりません。
4. **すべての境界の両側と、すべてのブール判断を検査します。** 宣言された制限には、最小、最大、内側ぎりぎり、外側ぎりぎりのケースが必要です。
5. **各アトミックな境界で故障を注入します。** 各故障の後で不変条件を確認します。拒否されたコンパイル、ロード、tick、リセット、ホットスワップ、永続化の操作は、部分的な状態や部分的な出力の集合を黙って確定してはなりません。
6. **不正な形式や変異したアーティファクトを、通常の敵対的な入力として扱います。** ローダーは、パニックせずにそれらを拒否するか、別個の有効なモジュールとして受け入れなければなりません。変異がそのソースと等価であると決して仮定してはなりません。
7. **独立した実装やターゲットを、同じアーティファクトと同じ入力トレースで比較します。** ネイティブとWASMは一致しなければなりません。両ターゲットは同じコアからセマンティクスを共有しているため、その共有されたセマンティクスについては別個のオラクルが依然として必要です。
8. **テスト自体を測定します。** 分岐／条件カバレッジとミューテーションテストは、再現可能なコマンドと正当化された除外がチェックインされた時点で、リリースゲートになります。テストの数からカバレッジの割合を推測してはなりません。
9. **修正されたすべての欠陥に回帰テストを付けます。** 修正が受け入れられる前に、最小で恒久的な回帰ケースが必要です。
10. **リリース用スイートはリリースビルドで実行します。** リリースモードのアーティファクトと、利用者が配備するのと同じ機能構成を使用してください。

この方針は、SQLiteの要件カタログ、TH3による配備状態でのテスト、境界および故障注入のループ、独立したSQL Logic Testによる比較、分岐／MC/DCカバレッジ、ミューテーションテストについての公開資料に着想を得ています。GhostFlowがSQLiteのカバレッジや保証レベルに達したと主張するものではありません。

参考資料：

- <https://www.sqlite.org/requirements.html>
- <https://www.sqlite.org/testing.html>
- <https://www.sqlite.org/th3.html>

## 要件レコード

`contracts/requirements/`配下の機械検査されるカタログは、各要件について次の情報を記録します。

- 正規化された規範テキストから導出された安定したID
- 規範テキストそのものと、そのドキュメント上の位置指定子
- 所有するレイヤーとサポートされるターゲット
- その記述を検査するテストのID、または空でない保留理由
- 検証済み、一部検証済み、保留中を区別するステータス

規範テキストを変更すると、新しいIDが作られます。以前のレコードは、置き換えられた履歴として引き続き参照できます。これにより、古いテストが証明した内容が黙って変わることはありません。

## 検証レイヤー

各レイヤーには、それぞれ独自の証拠が必要です。次の表は、各レイヤーの最低限の証拠を示します。

| レイヤー | 最低限の証拠 |
| --- | --- |
| 文法 | 正確な診断を伴う、受理および拒否されるトークン／ASTのケース |
| 型とローワリング | 型付きソースから、検査されたGFB構造とマニフェストまで |
| GFB検証器 | 有効な、切り詰められた、制限超過の、変異したバイト列 |
| ネイティブVM | 正確な状態、要求意図、安全意図、故障、アトミック性のトレース |
| WASM VM | ネイティブと同じアーティファクト／トレースとエラー分類 |
| ホストのライフサイクル | インストール、有効化、最初のスキャン、失敗したスキャン、リセット、ホットスワップ、リプレイ |
| 製品アダプタ | 識別された言語アーティファクトのみ。評価器の重複なし |
| デバイス | 別個のビルド、ボード／プロファイル、ドライバ、物理観測のゲート |

## 出力の安全規則

**出力宣言とは何か。** 出力宣言は、論理的な意図ポートに名前と型を与えます。状態は保持しません。物理リレーの起動時レベルやフェイルセーフレベルを設定することもありません。宣言されたすべての出力は、スキャンごとの接続式をちょうど1つ持ちます。定数の意図を出力するには、定数の接続式を記述してください。

**最初のスキャンが成功する前。** この時点では、VMの出力意図はまだ存在しません。ホスト／レンダラーは、設定された安全状態を保持しなければなりません。Farm Deviceの既定の方針はOFFです。コンパイル、ロード、有効化、tickのいずれかが失敗しても、ソースの構文から意図を作り出すことはできません。

**物理的な安全の責任者。** 物理的な起動、ウォッチドッグ、フェイルセーフの方針は、識別されたホストバインディングに属します。これらは、ポータブルなVMプログラムとは分離されたままです。
