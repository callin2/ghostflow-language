# 8. FAQ 요구와 언어·실행·장치의 책임

[전체 목차](../LANGUAGE-REFERENCE.md) · [이전: 의미 보존 규칙과 색인](07-semantic-rules-and-index.md)

이 장은 [Coding FAQ](../language_faq.md)의 요구를 언어, 도구, 런타임, 실행 환경,
Driver, 설치 연결, UI가 각각 무엇을 책임져야 하는지로 분류한다.
구현 진척이나 특정 저장소의 코드 배치를 정의하지 않는다.
각 기능의 문법과 의미는 연결된 Reference 절을 따른다. 이전 설계 스케치와 다른 표기가
나오면 이 Reference에서 확정한 표기를 사용한다.

## 8.1 분류 원칙: 의미와 실행 수단

**언어는 프로그램이 무엇을 뜻하는지 정하고, 런타임은 그 의미에 따라 판단한다.**
Driver와 실행 환경은 판단에 필요한 사실과 시간을 제공하고 출력 효과를 적용한다.
특정 연산이 VM 내부에서 실행되는지 호스트 어댑터에서 계산되는지는 이 의미의 소유권과 별개다.

예를 들어 “매일 현지 시각 6시에 한 번 시작한다”는 언어의 예약 의미다.
시계·시간대 자료를 어디서 얻는지는 실행 환경의 책임이다.
어댑터가 예약 발생을 공급하더라도 중복 억제·관측 누락·DST 정책은 같은 언어 계약을 따라야 한다.
화면이나 Driver가 별도의 규칙으로 시작 여부를 재해석하지 않는다.

FAQ의 `input is_holiday: Bool`, `input used: Duration` 같은 단편은 **값을 소비하는 법**을 보인다.
선언만으로 공휴일 계산기나 누적 기록이 생기지는 않는다.
입력 생산자의 의미·유효성·시간·복구 계약까지 있어야 해당 요구를 온전히 지원한다.

사용자가 선택할 정책도 구분한다. 취소 후 어느 장치를 움직일지, 하루 한 번 세척할지,
작동 시간을 변경하면 진행 중 작업에도 반영할지는 작성한 프로그램의 선택이다.
이 사례마다 새 키워드나 내장 제어 모드를 만들 필요는 없다.

**왜:** 문법을 추가해도 시계나 물리 피드백은 저절로 생기지 않는다. 반대로 Driver가
값을 읽을 수 있어도 프로그램에 시간·오류·상태 의미가 없으면 일관된 제어를 설명할 수 없다.

## 8.2 계층별 책임

| 계층 | 반드시 맡는 책임 | 다른 계층과의 경계 |
|---|---|---|
| 언어 사양 | 타입·상태 전이·시간·오류·설정·출력 의도의 의미, 자원 한계와 실패 규칙 | 장치 주소, UI 모양, 저장 매체를 제어 문법으로 만들지 않는다. |
| 컴파일러·도구 | 정본 문서 해석, 타입·이름·분기 검사, 실행 표현으로 변환, 선언·의도·설정 설명 보존 | 물리 배선이나 실제 작동을 정적 타입 검사만으로 증명하지 않는다. |
| 제어 런타임 | 입력 snapshot으로 상태·식·타이머·제약을 평가하고 결과를 원자적으로 확정, 설정 event와 관찰값의 실행 위치 유지 | 임의로 프로그램 정책을 추가하거나 출력을 물리 확인으로 간주하지 않는다. |
| 실행 환경·데이터 제공자 | 시계와 신뢰도, 날짜·자연 사건 자료, 실행 수명, 설정·checkpoint·설비 기록의 저장과 복원 | 공급한 자료의 판본·적용 범위·유효성·실패를 드러낸다. 별도 제어 언어를 만들지 않는다. |
| Driver | 장치 통신, 원시 신호 해석·정규화, 샘플 식별·시각·품질, 출력 적용 결과, 부팅·장애 시 물리 출력 | 제어 순서·인터록·날짜 정책을 소스 밖에 숨기지 않는다. |
| 설치 profile·binding | 논리 역할과 실제 endpoint 연결, capability·극성·범위 등 호환성 및 설치 판본 | 연결만 바뀌는 것과 소스 규칙 변경을 구분한다. |
| UI·renderer | 설명된 타입·라벨·범위·권한으로 편집·표시, typed 요청 제출, 결과와 오류 표시 | 별도 타이머·집계·제약 판정으로 제어 의미를 재생성하지 않는다. |

여기서 **실행 환경(host)은 제어 프로그램을 실행시키는 장치 또는 프로세스**를 뜻한다.
Android 게이트웨이나 클라우드를 필수 구성으로 뜻하지 않는다.
장치가 필요한 시계와 유효 자료를 로컬에 갖고 있으면 인터넷 없이도 계약을 이행할 수 있다.
네트워크 단절과 자료 만료·시각 불명은 각각 다른 상태다.

## 8.4 기능별로 지켜야 하는 경계

### 일반 제어 조합과 내장 기능

자기유지, 탱크 충전, 단계별 취소는 기존 state·Bool·enum·case의 조합이다.
런타임은 상태 전이 의미를 제공하고 작성자는 재시작·취소·완료 정책을 선택한다.
Driver에 별도 자기유지나 취소 순서를 숨기지 않는다.
FAQ의 Bool 알람 래치도 자동으로 alarm record나 외부 통지 서비스가 되지는 않는다.
FAQ 11의 `done`은 3회에 도달한 뒤 유지되는 Bool 값이며 1회성 완료 펄스가 아니다.
3에서 계수를 멈추는 것도 그 예제의 조건식이며 Int 연산 자체의 포화 규칙이 아니다.
에지 카운터는 런타임이 관측한 입력 변화를 센다. 판단 사이에 발생했다 사라진 물리 펄스까지
세어야 한다면 Driver·입력 생산자의 캡처와 전달 계약이 필요하다. 정확 정수 타입만으로
물리 사건의 무손실 관측을 보장하지 않는다.

**왜:** 응용 사례마다 특수 명령어를 만들면 같은 상태 전이를 여러 의미로 관리하게 된다.
근거: [§2.8](02-types-expressions-state.md#28-tick과-상태-snapshot),
[§5.3 event와 alarm](05-settings-and-observation.md#event-command-result와-alarm).

### 시간 판단과 자료 제공

언어는 단조 시간과 지역 날짜를 구분하고 DST·fallback·발생 identity를 정의한다.
실행 환경은 신뢰 가능한 시간과 달력·예측 자료를 공급한다.
일정 계산의 일부를 어댑터에 배치하더라도 같은 자료·시간·기록에는 같은 결과여야 한다.
생성 입력은 원인과 판본을 잃은 임의 Bool 펄스로 축소하지 않는다.

**왜:** 시계를 얻는 방식이 바뀌어도 중복 실행·누락·운전 길이의 의미가 바뀌어서는 안 된다.
근거: [§3.1](03-time-and-schedules.md#31-시간값과-시계-영역),
[§3.5](03-time-and-schedules.md#35-schedule의-공통-의미),
[§3.9](03-time-and-schedules.md#39-solar-달과-조석).

### 누적 사용량과 지속 저장

언어 계약은 무엇을 셀지(requested/safe/applied/confirmed), 범위와 날짜 경계,
초기화·불명 상태를 정한다. 제어 내부의 에지 카운터는 일반 state로 계산할 수 있다.
여러 control과 모드에 걸친 영속 설비 ledger는 실행 환경의 제공자가 안정적인 설비 identity와
Driver의 적용·확인 증거로 갱신·저장·복원하고, 제어 런타임에는 식별된 집계 snapshot을 공급한다.
제공자 내부의 순수 집계 계산도 같은 언어 계약을 따르며 저장 매체가 집계 의미를 바꾸지 않는다.
장치 한 대의 사용량은 자동·수동 제어별 요청을 더하는 것과 다르다.
화면이 켜져 있던 시간을 합산하여 설비 사용량으로 대신하지 않는다.

**왜:** 실행 상태의 일시적 기억과 재시작을 넘어 지켜야 하는 설비 기록은 수명이 다르다.
근거: [§3.4](03-time-and-schedules.md#34-누적-시간과-rolling-budget),
[§3.10](03-time-and-schedules.md#310-시간-기반-사용량-제약).

### 설정·검증·화면

언어가 타입·허용 범위·증분·권한·라벨을 선언하고 도구가 그 설명을 보존한다.
실행 경계는 요청 전체를 검증하고 런타임은 승인된 값을 같은 Program/run에 원자적으로 적용한다.
UI의 사전 검증만으로 승인하지 않으며, 컴포넌트를 바꿔도 같은 조건을 적용한다.
진행 중 작업에 새 duration을 읽을지 시작 시 값을 기억할지는 프로그램의 제어식이 정한다.

**왜:** 시간 입력창을 슬라이더로 바꿔도 허용되는 값과 실행 결과가 같아야 한다.
근거: [§5.1](05-settings-and-observation.md#51-config-선언),
[§5.2](05-settings-and-observation.md#52-소스-변경과-운영-설정-변경).

### 장치 독립성과 실제 효과

컴파일된 Program은 논리 역할을 사용한다. 직접 GPIO, 확장 채널, RS485 장치 주소는
설치 binding과 Driver의 책임이다. 호환 교체만으로 소스 수정·재컴파일을 요구하지 않는다.
새 논리 port나 새로운 제어 동작을 추가하는 일은 소스 변경이다.
논리 결과의 원자적 확정, 버스 명령 적용, 실제 접점·기계 동작 확인은 서로 다른 사실이다.

**왜:** 장치 접근을 추상화해도 물리 지연과 실패가 사라지는 것은 아니다.
근거: [§4.7](04-sensors-constraints-control.md#47-requested-safe-applied-confirmed),
[§6.3 호환 교체](06-composition-and-replay.md#호환-장치-교체와-재컴파일-독립성).

## 8.5 변경과 재시작의 생명주기

| 변경 또는 데이터 | 의미의 소유자 | 판본·실행·보존의 경계 |
|---|---|---|
| 제어식·센서 필터·stale_after·소스 기본값 | 언어와 정본 소스 | 새 source revision; 실행 규칙이 바뀌면 새 Program 후보 |
| operator config의 유효값 | 언어의 live 설정 계약 | 같은 Program/run, 새 settings revision; 일반 설정은 실제 재시작 후 보존 |
| 호환 센서·GPIO·릴레이·버스 채널 연결 | 설치 binding과 Driver | 해당 설치/Driver 판본 변경; 같은 Program 재사용, 무정지·동일 run까지 보장하지 않음 |
| state·타이머·필터 내부 기억 | 언어 실행 의미 | 실행 중 갱신; 재시작 복원은 명시한 정책과 checkpoint 계약 필요 |
| 예약 중복 기록·설비 사용량 | 언어의 설비 기록 계약과 실행 환경 | 일반 state 초기화·소스 교체와 독립된 수명; 계약 없는 초기화 금지 |
| 달력·조석 예측 자료 | 제공자와 이를 소비하는 시간 계약 | 자료 revision·coverage·expiry와 사건 identity 유지 |
| 라벨 선언 / 컴포넌트 모양 | 소스 metadata / renderer | 라벨 소스 편집은 문서 판본 변경; 화면 모양은 제어 의미를 바꾸지 않음 |

이 구분은 파일 개수를 정하지 않는다. `.ghost.md`가 정본 소스라는 규칙과 별도로,
설치 정보·설정 override·실행 기록의 저장 형식은 해당 환경이 정한다.
펌웨어 갱신, Driver 갱신, Program 교체, settings 변경을 같은 종류의 업데이트로 간주하지 않는다.

센서·필터·freshness는 재부팅 뒤 기본적으로 초기화하고 `NotReady`부터 다시 준비한다.
센서 상태의 persistent resume은 source/time continuity를 검증하는 명시적 선택이다.
일반 checkpoint가 있다는 이유만으로 오래된 정상값이나 필터 연속성을 복구하지 않는다.

## 8.6 언어 결정과 작성자가 정하는 정책

타입·문법·평가·시간 경계는 언어가 정한다. 아래 운전 정책의 실제 값은 프로그램
작성자나 설치 운영자가 정한다. 필요한 정책값을 생략한 선언은 거부하며, UI나 런타임이
사용자 대신 자동 운전 방침을 만들어 넣지 않는다.

| 대상 FAQ | 확정한 언어 계약 | 작성자 또는 실행 환경이 제공할 것 |
|---|---|---|
| 11, 23 정확 횟수 | §2.3의 Int·명시 변환·오류 규칙 | 무엇을 한 번으로 셀지, 세척 포함 여부, 매 N회 또는 하루 한 번 |
| 21, 27–29 요일·공휴일·DST | §3.8의 날짜·달력·gap/fold 계약 | 현장 시간대, 사용할 달력과 판본, 겹치거나 없는 시각의 운전 선택 |
| 24 운전 길이와 예약 시각 | Duration config와 §3의 typed 슬롯 설정은 서로 다른 타입; 모두 atomic live event | 공개할 설정, 범위, 실제 운전 시간·예약 시각 |
| 30–31 조석·달 | §3.9의 사건·기간·fallback·발생 identity | 예측 지점·자료, 사리/조금 분류 기준, 자료가 없을 때 허용할 동작 |
| 22 누적 시간 | §3.4·§3.10의 범위·집계·경계·영속 기록 | applied 또는 confirmed 등 증거 기준, 한도와 불명 구간 처리, 저장 매체 |
| 23 일일 횟수와 세척 | 정확 횟수·날짜 경계·단계·요청 기억을 조합 | 세척 순서·장치·중단 조건·세척 완료 인정 기준 |
| 32 정전 후 재개 | §5.2의 새 run·초기화·원인 입력·명시 checkpoint 복원 | 자동 재개 또는 새 시작 대기, 복원 허용 범위, 물리 부팅 출력 |
| 33 온도 센서 | §2.9의 물리량 타입·단위와 §4의 Result | 논리 계약을 만족하는 장치·Driver와 실제 설치 증거 |
| 34–40 연결·교체 | §6.2–6.4의 논리 port·외부 binding·재컴파일 독립성 | 설치 저장 형식·실제 핀/주소·Driver 배포 방식 |

이 표의 운전 선택은 언어 설계의 미결정 사항이 아니다. 한 가지 전역 답으로 고정하면
서로 다른 설비의 의도를 바꾸게 되므로 소스·설치 계약의 명시적 인자로 남긴다.
저장 매체, UI component, 통신 protocol도 언어 문법을 결정하기 위한 선행 조건이 아니다.

### 사용자 판단을 대신하지 않는 항목

- 정전·fault·취소 뒤 재가동 여부와 실제로 움직일 장치.
- 운전 시간·횟수·세척 조건·시간대·달력·자연 사건 자료와 대체 동작.
- 센서 허용 품질·최대 age·추정 허용 오차와 물리 피드백 기준.
- 공유 자원의 대기·선점·권한, PI/PID 목표·gain·출력 한계와 장애 동작.
- 임시 설정의 값·수명, 자동 보정이 바꿀 범위·속도·승인 권한.

이 값이 필요한 프로그램을 작성할 때 사용자 의도를 확인한다. 문법·타입·오류 규칙을
정하기 위해 현장별 값을 지금 일괄 선택할 필요는 없다.

근거: [§2.3](02-types-expressions-state.md#23-정확한-정수-설계),
[§2.9](02-types-expressions-state.md#29-물리량과-단위),
[3장 시간 계약](03-time-and-schedules.md),
[§5.2 생명주기](05-settings-and-observation.md#생명주기와-임시-설정).

## 8.7 새 요구를 분류하는 순서

1. 기존 식·상태·타이머로 조합할 수 있는 사용자 정책인지 확인한다.
2. 다른 실행 환경에서도 같아야 할 의미가 추가되는 경우 언어 계약과 Why를 명시한다.
3. 시간·센서·달력·예측·집계 입력마다 생산자와 유효성·오류·판본을 명시한다.
4. 실행 중 기억과 재시작 후 보존할 기록을 나눈다.
5. 실제 장치 연결·출력 효과는 Driver와 binding 계약으로 연결한다.
6. UI에는 같은 의미의 descriptor와 관찰 결과를 제공하고 표시·입력 방식을 맡긴다.

**판단 기준:** 동일한 Program, 입력·논리 시간·설정 event와 시작 상태를 주었을 때
같은 제어 판단을 설명할 수 있어야 한다. 장치나 UI의 종류가 그 판단에 숨은 차이를 만들면
언어 의미와 환경 책임의 경계가 충분히 정의되지 않은 것이다.
