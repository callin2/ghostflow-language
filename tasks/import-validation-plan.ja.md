# ピン留めされたインポートの検証

基準：Language Reference §6.4–6.7。この文書は実装の進捗と計画を追跡するものです。言語仕様を置き換えるものではありません。

**この文書の読み方。** 最初のセクションは現在の状態（2026-09-23）を説明します。以降のセクションは、それ以前のマイルストーンの記録で、履歴として残しています。その中の「REF-06-010 は RED のまま」「lowerer は解析されたすべてのインポートを拒否する」「公開の sourceClosure API はない」といった記述は、そのマイルストーンの時点では正しかったものであり、現在の状態によって置き換えられています。

## 現在の実行可能スライス（2026-09-23）

**状況。** REF-06-010 は現在、CLI の check と成果物のビルドに合格します。以下の古い未サポート経路に関する記述は、以前のマイルストーンを説明したものです。

**ソースクロージャ。** `compileSource` は明示的な `sourceClosure: [{ filename, revision, text }]` を受け付けます。

- ブラウザで安全なコードを使い、正確なダイジェストとリビジョンを推移的に検証します。
- ファイルやネットワークのリソースは取得しません。
- CLI はそれらの正本ドキュメントをファイルシステムから収集します。

**合成のサポート。** AST の合成は次をサポートします：

- スカラーの入力/出力ポート
- パラメータ
- 状態式と let 式
- ネストしたインスタンス
- 必須の入力
- 正確なポートの型
- 書き込み元は 1 つ

組み合わせ的な循環と、インスタンスをまたぐ次状態のフィードバックは拒否されます。ドキュメントとインスタンスごとのソースノードは、成果物のマップ内で別々に保たれます。

**成果物の復元。** 復元では、クロージャ全体を再コンパイルし、成果物を受け入れる前にバイトコード、マニフェスト、トレース、来歴を比較します。

**クロージャの上限。**

| 上限 | 制限値 |
| --- | --- |
| ドキュメント | 128 |
| ソースの合計 | 8 MiB |
| インスタンス | 128 |
| 式変換の訪問数 | 65,536 |

**テスト。** `tests/composition-execution.test.mjs` は、Rust WASM の状態の分離、推移的なソース解決、不正な接続、欠落した入力、引数のエラー、未使用出力の型チェック、成果物/来歴の改ざんをカバーします。

**センサと純粋関数の合成**は [#377](https://github.com/callin2/ghostflow-language/issues/377) で追加されました。

- ルートの生パケットは、インスタンスごとの独立したコンディショナに分配（ファンアウト）されます。
- 公開センサは `manifest.sensors` に残ります。非公開のディスクリプタは `manifest.sensorInstances` にあり、`sourceSensor`、`instance`、`port` を持ちます。
- ペイロード、オプション性、宣言されたサンプリング間隔が一致しなければなりません。
- 関数のパラメータと case のバインディングはレキシカルなままです。
- 対象を絞ったカバレッジには、独立したフィルタリング、故障、復旧、stale（古い値）、スキャンのロールバック、非公開パケットの拒否、ソースの復元、実際にコンディショニングされたフレームのネイティブ/WASM 比較が含まれます。
- GFB/ABI/フレームのプロトコルは変更されていません。

**まだサポートされていないもの：**

- timer/schedule/config/enum/resource/constraint 宣言の合成
- インポートされた意図リンクの展開
- 修飾された公開関数/型のエクスポート

これらは、インスタンスの意味論を黙って失うのではなく、明示的に失敗します。インポートされたリビジョンラベルは、供給されたクロージャの同一性と照合されます。その真正性については、呼び出し側またはカタログが責任を負います。

## 実装済みのパーサスライス

*過去のマイルストーン。*

`ControlParser` は、トップレベルのピン留めされたインポートヘッダを受け付け、それらを別の `imports` AST リストに保持します。各エントリは次を保持します：

- エイリアス
- 相対 `.ghost.md` ロケータ
- リビジョン
- ダイジェスト
- ソースノードの同一性
- すべてのピンフィールドのトークン位置

次のエラーを、記述されたトークンの位置で報告します：リビジョン/ダイジェストの欠落、不正なダイジェスト構文、空/latest のリビジョン、非正準/絶対/ネットワークのロケータ、重複したエイリアス。既存の文芸的（literate）ソースの診断リマッピングが適用されます。

lowerer は、解析されたすべてのインポートをコンパイル前に次のメッセージで拒否していました：
`import execution requires a verified source closure and composition lowering,
which are not yet supported`。未使用のインポートも含め、インポートが黙って無視されることはありませんでした。空でないリビジョン文字列を解析できても、リゾルバのリビジョンが不変であることの証明にはなりません。

- `build/import-header-green.log`：対象を絞ったテストと影響を受ける構文テスト 272/272 が合格。`tests/import-header.test.mjs` の新しい 14 テストすべてを含みます。
- 新しいスイートは `tools/verify-language.mjs` に明示的に登録されています。

このマイルストーンの時点では、REF-06-010 にはまだ受理される合成がありませんでした。その受け入れ期待値と、その他すべての Reference の期待値は変更されていません。

## パラメータと合成の構文スライス

*過去のマイルストーン。*

**パラメータ。** `parameter` の既定値は型付きの不変値としてコンパイルされ、オペレーター設定とは独立に `manifest.parameters` に記録されます。

- パラメータの前方参照は、宣言順序に依存せずに解決されます。
- 循環する既定値、型の不一致、入力・状態・可変な config への依存は拒否されます。

**合成の構文。** パーサは、`instance` 宣言、名前付きの特殊化引数、`connect` のエンドポイントを、元のソース位置とともに保持します。ローカルな合成の検証は次を拒否します：

- 未知のインポートエイリアス/インスタンス
- 重複したインスタンス宣言と引数
- 不正なルートポートの方向
- 競合する供給元（式と `connect` の両方で定義されたルート出力を含む）

**このマイルストーンでの制限。** 公開コンパイラは、検証済みのソースクロージャがない有効なインポートを依然として拒否していました。インポートされた引数の名前/型、必須ポート、正確なポートとセンサの契約、インスタンスの分離、実行可能な合成については、達成を主張していませんでした。

**証拠。**

- REF-06-010 は RED のままでした。
- REF-06-103 は、実際の重複供給元の診断で合格するようになりました。
- `tests/import-composition.test.mjs` には、合格する対象を絞ったテストが 21 個あります。
- インポート/ヘッダ/ダイジェスト/control/コンパイラを合わせた実行は 42/42 で合格します。

## 次の最小実装境界

*過去の計画。*

当時、環境に依存しない `tools/compile-source.mjs` は 1 つの正本ドキュメントだけを受け付け、リゾルバ/ソースクロージャの入力を持っていませんでした。`tools/ghostc.mjs` はルートドキュメントだけを読み込んでいました。完全な次のスライスには、次が必要でした：

1. 明示的な供給ドキュメントのクロージャ契約。各ドキュメントについて、正本のファイル名/ロケータ、不変のリビジョン同一性、元のテキスト、検証済みの UTF-8 ダイジェストを運びます。ブラウザと Node で同じ検証器を使います。検証器は、ファイルやネットワークのデータを暗黙に取得してはなりません。
2. （当時は未サポートだった）インスタンス本体を解析せずに再利用できる、インポートヘッダの抽出。正規表現のスキャナではなく、パーサのトークン規則を再利用します。
3. インポート元ドキュメントを基準とした相対ロケータの解決。解決先は供給されたクロージャの中だけです。ロケータの綴りはソースの同一性ではありません。
4. 依存関係の欠落、リビジョンの不一致、ダイジェストの不一致、曖昧なロケータのバインディング、推移的なインポートの循環に対する診断。それぞれインポート元のソース範囲を保持します。ルートのインポートだけでなく、推移的な依存関係も検証します。検証済みの結果には、元の完全な散文と同一性を保持します。
5. クロージャを検証しつつも、合成の lowering/来歴が実装されるまではインスタンスの実行を依然として拒否する、公開コンパイラの統合。CLI のファイルシステム収集は、その同じ契約へつなぐ別のアダプタです。

**必須のテスト。** 有効な 2 階層のピン留めクロージャと、個別に分離した各破損を対にします。ダイヤモンド型の再利用、異なる定義でのエイリアスの再利用、パスの正規化、循環、バイト/ドキュメントのリソース境界もカバーします。検証は供給されたクロージャを変更してはなりません。

入力契約は、依然としてメインの統合担当者が決める設計判断でした。パーサスライスは、推測に基づく公開リゾルバ API を追加していません。

その後、REF-06-010 にはさらに、instance/parameter/connect の解析、インスタンスごとの状態の分離、正確なポート/品質のチェック、依存関係の順序付け、推移的な次状態の制限、書き込み元は 1 つ、ソース/リビジョンの来歴が必要でした。ソーステキストを平坦化して元のドキュメントの同一性を捨てることは、受け入れられる近道ではありません。

## CLI での直接ダイジェスト事前チェック

*過去のマイルストーン。*

この小さなスライスは `tools/ghostc.mjs` にあります。未サポートのインスタンス本体を解析する前に、CLI は次を行います：

1. `parseControlImports` を再利用してインポートヘッダを調べる。
2. 直接の各相対ロケータを、インポート元のルートファイル名を基準に解決する。
3. ピン留めされた SHA-256 を元のファイルのバイト列と比較する。

インポートされた散文、UTF-8 エンコーディング、CRLF のバイトは、そのまま比較に参加します。不正な UTF-8、サイズ超過のドキュメント、読み取れないファイル、ダイジェストの不一致は、成果物が公開される前に、記述されたインポートトークンの位置で拒否されます。

このマイルストーンの時点では、これはファイルシステム上の直接の完全性検証にすぎませんでした。公開の sourceClosure API、再帰的なリゾルバ、リビジョンの真正性の証明、受理される合成はありませんでした。一致した依存関係も、既存の未サポートのコンパイラ経路に到達していました。ブラウザでのコンパイルは、この CLI ヘルパーを通じてファイルを取得しません。

**証拠。** `tests/import-cli-digest.test.mjs` は、変更されていない REF-06-102 フィクスチャを check と build の両方のモードで実行します。正確な UTF-8/CRLF の一致、インポートされた散文の改ざん、既存の成果物の保持、欠落したファイル、不正な UTF-8 をカバーします。

- `build/import-cli-digest-red.log` には、4 件の失敗と、もともと合格していた未サポート経路の対照ケース 1 件が記録されています。
- `build/import-cli-digest-green2.log` には、156/156 の合格テストが記録されています。新しい 5 ケースすべて、インポートパーサのカバレッジ、既存の CLI 構文診断スイート全体を含みます。
- Reference の期待値は変更されていません。
